# aurix-debugger (B)

The standalone debugger: a GPUI window on the probe-rs DAP server.

| Part | What it does |
| --- | --- |
| Toolbar | Continue, Pause, Step Over (line), Step Instruction, Step Into Instruction of the selected thread; the connection state, the attach file, Disconnect |
| Attach page (no session) | The attach files used before, newest first, each with its chip and the program of each core (`%APPDATA%\aurix-debugger\recent.txt`); "Open attach file…" (a file dialog); the server address; why the last attach failed. A click attaches. Attaching the same file again sends its breakpoints again; another file starts without them and with its own Live Watch expressions |
| Threads | One thread per core, with its state (running, stopped and why); a click selects it |
| Call stack | The frames of the selected thread; a click shows the frame's source, disassembly and variables. Under each frame its local variables (its Locals scope, the first level, at most 8 shown; TRACE32's `Frame.view /Locals`), the values of an outer frame as they were at its call; a value that differs from the last stop its function was in is red. "Locals" turns them off (no requests then) |
| Source | The frame's source file (read from the path in the debug information) with its line marked (▶), back to it with PC, Reload after an edit; a click left of a line sets or removes a breakpoint on it (● set, ○ refused). A right click there opens the breakpoint's edit row: a condition (`v == 3 && k != 0`), a hit count (`3`, `>= 3`, `% 4`) and a log message (`v = {v}`, the core does not stop); Enter or Set sends them, Remove removes the breakpoint. ◆ marks a breakpoint with a condition or hit count, blue ◆ a log point, ◇ one the server refused (the reason shows in the edit row and the console). probe-rs checks them at each halt and runs the core on when they are not met |
| Disassembly | The instructions around the frame's program counter (▶), read further with ▲/▼, back to the PC; a click left of an instruction sets or removes a breakpoint on it (● set, ○ refused); ◆ marks where a source line's breakpoint was set |
| Variables | The frame's scopes (Static, Peripherals, Registers, Variables) as a tree; a click expands or collapses a node, what is expanded stays so at the next stop, and a value that differs from the previous stop's is red (locals and registers: same function on the same core; statics and peripherals: same core) |
| Console (tab) | The server's messages and stop descriptions (the same message twice within 500 ms shows once), and the lines of log points (each one) |
| RTT (a tab per channel) | The lines of each RTT up channel of every core, following the newest; Clear. When the core has a down channel, a line typed below (Enter) is sent to it (`rtt write`, probe-rs adds the line break) and shown as `» line` |
| Memory (tab) | 256 bytes from an address typed in (hex, `0x` optional, `@core` optional) or from a variable's "mem", read every 500 ms while the tab is shown, the cores running or not; through the core chosen, so `0xD000A000` reads that core's scratch-pad RAM; ◀/▶ move by 256 bytes; a byte that changed is red until the next change; the address asked for is marked. A click on a byte selects it; hex bytes typed into "Write at" (Enter) are written there through the same core, if they are all in RAM of the TC27x (scratch-pad RAMs, a core's local addresses, LMU); flash, the UCBs, peripheral registers and anything else are refused before anything is sent |
| Live Watch (tab) | Expressions (global variables) read every 500 ms on every core while the cores run; a value that changed since the last read is red; typed into the input (Enter), or sent from a Static variable with "watch"; × removes one; reading can be paused. The expressions are kept next to the attach file (`<attach>.watch`) |
| OS (tab) | The OS objects of an ORTI file (2.1, 2.2): a table per object kind (OS, tasks, ISRs, …) with a column per attribute, read every 500 ms while the tab is shown, the cores running or not (probe-rs `liveWatch` reads the C expressions of ORTI files: paths such as `OsTcb[1].prio` and `OsRunningTcb->state`, an index read from the target `OsTcb[OsCurrentTask].prio`, `&`, casts such as `(unsigned)OsTicks / 2` and `*(uint32 *)0x70001000`, C's operators and `?:`); ENUM values by name, an ENUM item whose value is an expression (`"TaskA" = "&OsTcb[0]"`) names the value equal to what it reads, a value that changed since the read before is red, an expression the server cannot read (a function call, a type of unknown size behind `*`) shows why in its own cell. An object whose name is a software trace id (SW Trace tab, `<attach>.trace`) gets two columns more: its load and its last run, measured by the trace. "ORTI file…" chooses the file; its path is kept next to the attach file (`<attach>.orti`, relative to its folder). Without one, or with one that cannot be read (the reason shows in the tab and the console), debugging is as before. Try it with `tc275_orti_demo.json` and the RAM program of `zed/aurix_tcf_demo/build_orti.ps1` |
| GTM (tab) | The eight channels of one MCS instance of the GTM (MCS0–MCS3 to choose): enabled, PC, R0–R7, the flags N V Z C, the stack depth, IRQ and ERR, read every 500 ms while the tab is shown, the cores running or not; a value that changed since the read before is red. A click on a channel shows the MCS code around its PC, disassembled (▶ at the PC). The memory layout (MCFG_CTRL) gives each instance's memory size. Stop and Run on a channel write its `CTRL.EN` (the only write of the tab): a stopped channel keeps its PC and registers and goes on from there. The whole GTM does not halt with the cores (the trigger switch's suspend routing is not public). The registers are read word by word through the probe-rs fork's `readRanges` request. Known for the TC27x GTM; other chips say so. Try it with `tc275_gtm_demo.json` and the RAM program of `zed/aurix_tcf_demo/build_gtm.ps1` (two MCS1 channels) |
| Cache (tab) | Per core: the program cache and the data cache (TC1.6P, TC1.6.2P) or data read buffer (TC1.6E), their sizes and whether they are on or bypassed, the scratch-pads, and the segments cached for code and for data (`PCON0/2`, `DCON0/2`, `PMA0/1`), read every 500 ms while the tab or the memory tab is shown, the cores running or not. Measure sets the performance counters' sources (`CCTRL`) for four windows of one refresh each, TRACE32's BenchMarkCounter: the program cache and multi-issue, the data side, the dispatch stalls, the branches and program and data memory stalls. It shows per core the hits and misses, the instructions per cycle, the stalls as shares of the cycles and the branches per 100 instructions, and puts `CCTRL` back (the only writes of the tab). The memory tab says when the memory it shows may be in a core's write-back DCACHE (a value shown can be older than the core's) or read buffer. The lines in a cache are not shown: their tags can be read only with the cache off and mapped (`MTU_MEMMAP`), and their format is not public. Known for the TC27x and the TC36x (two TC1.6.2P cores; out of reset both caches are bypassed, the program turns them on: `build_flash.ps1 -Board tc36x -Caches`). `crates/dap-client/examples/cache_view.rs` shows the same without the app |
| SW Trace (tab) | The software trace a program writes with `zed/aurix_tcf_demo/src/aurix_trace.h`: 8-byte records (STM0 time, id, arg) on an RTT up channel whose `dataFormat` is `BinaryLE` in the attach file, read while the cores run. Per core and id the count, the load (the share of the time in its spans since the last drop: TaskA 33 %, timer ISR 0.03 % on the demo), the interval between records and the spans from `AURIX_TRACE_BEGIN` to `AURIX_TRACE_END` (min, average, max, last); every event kept (20,000), newest first, with the time since the one before on its core (a virtual list: only the rows shown are drawn); the records the target dropped (no interval or span reaches across a drop). 10 ms, 100 ms, 1 s and 5 s switch to a chart of that last window, TRACE32's Trace.Chart: a row per core and id, spans as bars, single records as ticks, the time under it; ◀ and ▶ move it half a window earlier or later through the events kept (with Freeze, through what was frozen), Latest back to the newest. Trace data redraws the window at most four times a second. The ids are named by `<attach>.trace` (`id = name` a line). Freeze keeps the view while the trace is read on, Clear forgets what was read, Save CSV writes the events kept next to the attach file (`<attach>-trace.csv`). A binary channel has no RTT tab of its own. Try it with `tc275_orti_trace.json` and the RAM program of `zed/aurix_tcf_demo/build_orti.ps1 -Trace` |

The splitters between the panels (threads | center | variables, source / disassembly, the
bottom panel) are dragged to resize them and double-clicked to put them back; the sizes are kept
in `%APPDATA%\aurix-debugger\layout.json`, and a smaller window shrinks the panels so that the
center keeps its least.

The state and rules of the views are the shared crates' (`../crates`: `aurix-debug-model`,
`aurix-dap-client`); this crate only draws them and sends the requests.

## Run

```text
probe-rs dap-server --port 50000
start_in_flash.exe C:\work\aurix_tcf_demo\build\demo_flash.elf
cargo run -- ..\crates\dap-client\examples\tc275_demo_3cores.json
```

Both arguments are optional: without an attach file the window opens on the attach page; the
second argument names another server (default `127.0.0.1:50000`). Any attach arguments of the
probe-rs fork work, `rttEnabled` included (`tc275_rtt_cpu0_cpu1.json`), and `speed` (kHz): the
example attach files ask for 6000, the fastest clock of the ShieldBuddy's DAS adapter (the TAS
server's own is 400 kHz, about a third of the speed of steps and memory views).

## GPUI and licenses

GPUI comes from the Zed checkout next to this repository (`../../zed`, tag v1.25.3, path
dependencies); the patches and `Cargo.lock` are Zed's, so GPUI builds with the versions it was
released with. `cargo metadata` of this crate: 618 packages in the build graph, no GPL one; the
19 Zed crates among them (gpui, gpui_platform, gpui_windows, collections, sum_tree, …) are all
Apache-2.0; `r-efi` and `self_cell` are dual licensed with a permissive option. The license of
this crate and the shared crates is not decided yet (`publish = false`).
